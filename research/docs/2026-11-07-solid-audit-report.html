Executive summary

The architecture is sound; the implementation is over-concentrated. This is a small, deliberately layered research harness: 149 TypeScript files and 18,257 source lines, of which 10,569 (58%) are the React dashboard. Dependency direction is enforced in CI by Nx layer tags plus a custom ESLint rule and proven by scripts/verify-boundaries.mjs, which I re-ran during this audit and which passes. Services compose dependencies through ports (Repository, ModelAdapter, Scenario, PrivateMemory, ResearchStore), artifacts carry versioned provenance, and in-memory adapters make most logic testable without infrastructure.

The SOLID violations are concentrated in a handful of modules. Four dashboard pages — Analysis.tsx, Oversight.tsx, Experiments.tsx, Runs.tsx — are 6,877 lines (65% of the dashboard). Three of them contain a single component of 553–1,050 lines that owns data fetching, form state, validation, pagination, routing and six or seven mutually exclusive views. On the backend, HarnessScheduler.run() is a single 249-line method with thirteen responsibilities, and the API server is a 237-line module that is simultaneously HTTP transport, router, auth layer, body parser, static file server and launch-domain service. Nearly every high finding has the same shape: one function that is a system.

The most dangerous findings are not the largest ones. They are Liskov violations between interchangeable implementations: the in-memory and Mongo repositories disagree about missing runs (throw vs empty page), event-phase classification, replace() semantics, claim lifecycle, and whether an oversized attempt is rejected. The harness’s core value is evidence integrity, and the frozen-preview and staleness machinery depends on these ports behaving identically. Divergence here does not crash — it records, rejects or paginates evidence differently in tests than in production. Hash canonicalisation has the same problem: five sha256(JSON) helpers, two different key orderings, so “evidence unchanged” is not comparing the same thing everywhere.

The second systemic pattern is change amplification. Provider policy is restated in nine places across seven files and has already drifted (the declarative config schema omits providerOptions and stopSequences, which the validator accepts). Scenario identity appears in 30 production literals across 14 files. The two services contain a byte-identical copy of resolveInferenceProvider. Adding one supported provider setting currently means editing nine sites in seven files.

The front end repeats the pattern one layer down. Two abstractions — fetch and paginate — have six implementations: lib/api.ts, lib/paging.ts, three page-local hooks in Oversight.tsx, and four inline pagers in Analysis.tsx. The API “port” is a URL string with a caller-asserted type, five hand-built /api/… anchors bypass the transport entirely, and the Jev adapter invents contract values (revision: 1, archived: false, hardcoded input limits) so that its objects satisfy types the server never returns.

Verdict: C. The skeleton is well designed and mechanically protected; the organs are overgrown. Left alone, the cost is concentrated in four files that every feature touches, in policies that must be edited together, and in evidence paths whose behaviour depends on which adapter is in play. The P0 list is small and low-risk, and several P0 items pay for themselves immediately as deleted code.

Top risks

Findings grouped into the compounding risks that will actually shape future delivery.

01

The four largest dashboard files have no internal seams

Analysis, Oversight, Experiments and Runs are 6,877 lines — 65% of the dashboard and 38% of all source. Three contain a single 553–1,050-line component that owns fetching, form state, validation, routing, pagination and commands. Any UI change is a review and merge-conflict tax, and the lack of component-level data ownership is why the page tests stub global fetch and re-implement the endpoint table.

SRPDashboard
02

Evidence integrity rests on ports whose implementations disagree

The in-memory and Mongo adapters differ on missing-run behaviour (throw vs empty page), event-phase classification, replace semantics, claim lifecycle and the 1 MiB attempt bound. Unit tests run against the in-memory adapter, so these divergences are production-only. For a harness whose value is recorded evidence, a silent difference in what is recorded or rejected is the most expensive class of defect in the repo.

LSPShared packages
03

Change amplification: one policy, many edit sites

Provider policy appears in 9 places (already drifted), scenario identity in 30 production sites across 14 files, and the provider transport resolver is a byte-identical copy in two services. Adding a supported provider setting or a second scenario is a coordinated multi-file edit with no compiler help — the kind of change that half-lands.

OCPCross-cutting
04

Domain knows HTTP; transport owns policy

Domain exceptions carry status codes, the API infers status from error text with regexes, and the dashboard transport caches records and enforces review-admission rules. Layer inversion means the same rule exists twice, drifts, and cannot be tested where it lives.

DIPCross-cutting
05

Ports are mis-sized exactly where substitution matters

AnalysisRepository declares 28 methods but review code needs three; ResearcherRepository is 20 members but the healthcare route uses one; Repository lacks the three operations the worker loop calls, so the worker depends on the concrete Mongo class. Fat ports make fakes expensive and let fakes drift; thin ports push consumers onto implementations.

ISPShared packages
06

Two abstractions, six implementations in front-end data access

The dashboard has one real fetch and one real pager, plus a page-local fetch hook, a page-local cursor pager, a page-local offset pager and four inline pagers. Stale-response defences are therefore per-call-site and five export links bypass the transport entirely. This is the highest-value, lowest-risk cleanup in the repo.

DIPDashboard
07

Dead and aspirational code raises the maintenance floor

An unused Mastra starter agent with hardcoded model ids, an unused readyJob on a 28-method port, six unreferenced dashboard type exports, a half-wired artifact renderer registry, a declared-but-unimplemented demo mode and unused imports. Each one looks like a supported capability to the next reader.

domain/oversight/service.ts:10 · contracts/analysis/jev-repository.ts:44-48 · api/server/index.ts:244 · routes/oversight.ts:66-70 · routes/review-routes.ts:56

Evidence

OversightError carries an HTTP status (400/404/409/500) inside the domain package, and the analysis-domain exception classes do the same. Dependency direction is machine-enforced

Nx layer tags plus a custom ESLint rule reject cross-layer, cross-service, undeclared-export and browser/server leaks; scripts/verify-boundaries.mjs proves the rule with fixture sources and compiles the browser contract graph without Node declarations. I ran it during this audit: it passes.

Composition through ports at the hot seams

HarnessScheduler takes { repository, memory, adapter, scenario }, AnalysisWorker takes a repository plus injectable provider, the monitor worker takes store + provider, and the API server takes ResearcherRepository. The heavy unit tests substitute in-memory adapters with no infrastructure.

Concurrency is designed, not accidental

Launch-key idempotency, optimistic revision CAS for drafts/definitions, immutable sequence keys for reviews, fenced leases for analysis jobs, and frozen resolved configurations. This is unusually deliberate for a research prototype.

Versioned provenance everywhere

Normalizer, serialization, question-template, adapter and SDK versions are frozen into manifests; estimator and scoring versions travel with results; build provenance is attached to runs. Reproducibility has first-class fields rather than conventions.

Safety invariants live in adapters

Proposal-only tools are rejected at registration, provider SDK retries are forced to zero while application retries are bounded, sensitive-data filters wrap trace export, and credentials are rejected from model settings by the validator.

The healthcare slice is the model to copy

Pure rule modules (scoring, artifact validation, evaluation) with no I/O; strict parse → validate → evaluate pipelines; validation separated from resolution. It is the only area with no SRP finding.

Boundaries are documented and tested

The repo ships a boundary verifier, migration-equivalence and compiled-build verifiers, and 39 test files. The architecture is intentional; the gaps are inside modules, not between them.

Refactor roadmap

Ordered by risk-adjusted leverage. P0 is deliberately small: delete code, fix adapter parity, remove duplicate abstractions, then add guardrails so the ground does not re-accrete.

Method and limitations

  • Read-only static audit: no repository files were modified. Builds, unit tests and integration tests were not run because the integration suites require the MongoDB replica set; the boundary verifier was run because it is infrastructure-free.
  • Executed as four independent area audits (dashboard analysis/oversight, dashboard experiments/runs/codebook, backend services, shared packages) followed by lead verification: key claims and line references were re-read and spot-checked directly, and the duplicate-provider-transport claim was confirmed by file hash.
  • Line references were taken from the working tree at commit 20bc219 with 49 modified files (26 changed) present, so they describe the tree as audited, not HEAD.
  • Metrics are pattern counts over source files (excluding node_modules, dist and .nx): 149 TypeScript files, 18,257 lines. Generic-aware matching was used for hook counts; counts are exact for the files named, not for the whole repo.
  • Severity reflects maintenance and delivery risk, not security impact: critical = a module that is a system and will resist safe change; high = a concrete defect or change-amplification that will bite; medium = duplicated or mis-shaped abstraction; low = local hygiene.
  • No claim is made about the correctness of the research protocol, statistical validity, or runtime behaviour under provider load. Several LSP findings are contract-level and were established by reading both implementations, not by executing them.
